# Planning review and traceability

26 October 2026. Individual source/design review; no sub-agents, model-council runs, live model/provider checks, desktop tests or application execution were used. The 40-item risk register is a finite review, not a claim that every possible failure is eliminated.

## Review sequence

1. Read the user's pasted v4 plan and the current v4 C01–C23 requirements. Preserve them as plaintext references; their original contextual Markdown links are archived text, not navigation in the new package.
2. Inspect fetched GitHub UI/worker/server sources and the current uncommitted local backend/Electron client. Separate source presence, declared pins, reported historical verification and proposed product requirements.
3. Choose the new GitHub visual system and existing trusted application stack as the integration direction. Reject a production workbench proxy, second memory backend, duplicate approval authority and fixture-driven availability.
4. Define I0/I1 source/parity milestones and retain cumulative core R1–R7 inclusion rules. Record where actual limits are narrower than the reference draft, and where current service behavior does not yet meet the reference requirements.
5. Map every screen, feature, numbered worker and failure family. Record W01's naming/authority conflict and W10/W35's non-equivalence; no guessed bindings or new prompts.
6. Add U01–U12, specific acceptance scenarios and second-order risks. Link proposed containment to cases; keep implementation status Not run.
7. Check package links, unique IDs, references, coverage, source-read stability and default-disabled scope. Save only documentation/tables in the isolated branch.

## Design reconciliation decisions

| Conflict or new risk | Proposed resolution | Remaining proof |
|---|---|---|
| New design plus old client's feature set | Port the GitHub layout/tokens into one existing client; preserve functional forms/bridge and real data paths. | Rendered comparison, parity workflows and packaged interaction. |
| Current memory workspace versus chat-first R1 | Internal declared workspace-parity milestone; core R1 retains its strict surface/exclusions and is not claimed by parity. | Service-enforced manifest and release acceptance. |
| New workbench routes versus authenticated AppService | No production direct workbench fetch/store path; typed main/Python adapter only. | Sender/Origin/decoder/source-injection tests. |
| Two approval implementations | Persistent exact application gate is authoritative; upstream helper remains contract/fixture code unless explicitly adapted. | Forged/imported token denial and actual exact review. |
| 2-MiB current broker versus larger v4 draft | Start with one qualified UTF-8 source at actual minimum bounds. | Boundary/file/disclosure checks and future versioned expansion evidence. |
| Logical role name versus privileged identity | W01 Intent Analyst is not trusted orchestrator; overlapping document roles are not aliases. | Owner/schema/version reconciliation before actual binding. |
| Token file hash versus stable account | Use hash for configuration-change detection only; qualify real account identity/generation and scopes separately. | Actual account switch/revoke/reconnect tests. |
| Wall-only expiry and UI duplicate guards | Explicit service-level monotonic expiry and stable family-lock obligations. | Actual final admission tests across clients, clock changes, restart and pagination. |
| Existing retraction/artifact clearing versus complete forget | Keep accurate labels; add barrier/epoch/copy tracking and restore ledger gate before advertising Forget. | Disposable multi-store failure, lineage and restored-backup cases. |
| Rich workflow/scheduler/pet screenshots | Small linear reads first; real scheduler gate later; pet/native/research/fitness remain declared deferred/disabled. | Installed callback/effect proof, not presentation screenshots. |
| Erasure versus fine-grained uncertain-action dedup | Delete prose and widen minimal family lock conservatively. | Erasure, reconnect and duplicate-risk recovery probes. |

## Package consistency evidence

The generator checks **182 unique acceptance cases**, **40 proposed risk containments**, **47 unique numbered worker IDs**, **16 supplied upstream definition directories**, coverage of every C01–C23/U01–U12 identifier, risk-to-case references, authored local document links and **58 stable-during-read source fingerprints**. Counts and checks are recorded in PLAN-VALIDATION.json.

The first generator run encountered Git's ownership protection while reading the newly created checkout as the restricted sandbox user. It was corrected using a one-command exact-path `safe.directory` option for read-only `rev-parse`; no global Git configuration or ownership was changed. The generator does not import or execute application code.

Reference .txt files preserve source bytes. Source fingerprints are planning provenance, not a coherent implementation import or installed-runtime qualification. Contract/case coverage checks cannot prove design correctness, real performance, permissions, model quality or UI usability.
