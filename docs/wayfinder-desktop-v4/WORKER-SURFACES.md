# Workers behind the product

Workers are logical on-demand roles. The desktop UI is not an agent framework, replacement memory engine or permanent 47-process manager. Use installed Hermes routing/skills plus existing service enforcement. The [earlier established names and registry families](../wayfinder-desktop-v3/WORKER-SURFACES.md) remain the naming basis; no unknown role prompt is invented here.

The generated [47-ID inventory](WORKER-COVERAGE.csv) accounts for every planned numbered role as a supplied mapping or an unresolved mapping. It is a coverage checklist, **not proof that all workers exist or work**. Formal names/bindings/output schemas still require reconciliation by their owners before an Available badge. Existing unnumbered named aliases go through the same central versioned registry integration path; do not map them by guess or add competing registry edits.

| Fitness/activity | W26 | Explicitly deferred; no source chosen |
| Research/knowledge/notes | Existing planned named families; unresolved numbered mappings | Explicitly deferred connector slice; chat general knowledge is not live research |
| Security advice | W45 ownership example | Advisory findings only; trusted service enforces policy |

Each displayed binding needs version, effective tools, task/result schema, source of configuration, required connections/grants, budget policy, qualification tier/evidence and dependent workflows. Planned, configured, fixture-tested, live-qualified, unavailable, disabled and needs-review are separate states. A role's identity or a skill's text cannot approve an action. Missing inventory contracts remain a visible dependency rather than being recreated by the UI developer.

Ownership: platform/API/routing/permission services keep the supplied infrastructure responsibilities; worker developers keep task/result/prompt/fixture definitions. The redesign edits neither. Acceptance checks exercise these interfaces with synthetic fixtures before connecting live implementations.
