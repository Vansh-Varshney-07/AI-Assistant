1 Recommended foundation

Build a personal research and follow-through assistant around a memory service the user can inspect, correct, export, and delete. Use Hermes as the agent runtime, Nemotron 3.5 Lightning for routine work, and Nemotron 3 Ultra for bounded difficult tasks, both through Nebius Token Factory. Make the first complete workflow a research brief that remembers decisions and follows up on an explicitly chosen task.

Treat NemoClaw as the preferred managed sandbox integration if its pinned stack passes a short integration trial. Keep a simpler Hermes deployment as the delivery fallback. The differentiator should be useful, accountable memory and reliable follow-through. Installing several frameworks does not establish a useful product.

This is a proposed foundation, not a certification of the existing memory_system. Parent-conversation references to Iron Web establish context only. This research did not run its tests, inspect its current implementation, use credentials, provision cloud resources, or change the main project's source. All acceptance tests below are proposed work unless explicitly described as document checks.

Conditions for committing to the stack

Before building the full UI, verify that the account can call both exact model IDs, that a tool call completes through the intended sandbox, that the memory service is reachable under enforced policy, and that a restarted process can retrieve an earlier fact. Time-box this trial to half a day. If it fails, use direct Hermes with narrowly exposed tools and preserve the same memory API. This keeps the application portable.

4 Product definition and differentiation

Proposed product

Iron Web helps a person continue work across days without repeatedly explaining their projects. It creates short research briefs from chosen sources, retains user-approved facts and decisions, and follows up on a selected commitment. Every durable assertion has a visible origin and can be corrected.

Example: the user says, “For this project, prioritize privacy over latency. Review these three papers and prepare a brief tomorrow morning.” The assistant saves the preference with consent, reads the chosen material, proposes a reusable review procedure, and schedules the brief. On the next day it produces a source-linked draft. If the user changes the priority, subsequent recommendations reflect the newer decision.

This is a proposed use case, not evidence of customer demand. Validate it with three short user interviews and one real task from each person. Ask what they currently forget, which sources they trust, what they would let an assistant do unattended, and what would make them stop using it.

Minimum complete experience

1. Connect a selected folder or upload a small document set with a clear scope preview.

2. Ask a question and receive an answer with source references and uncertainty.

3. Save a preference or decision, inspect its record, then retrieve it in a fresh session.

4. Correct a stale fact and show the replacement in the next answer.

5. Schedule one recurring or one-shot brief with a visible next-run time and pause control.

6. Create a draft artifact; require approval before any external send or irreversible action.

7. Show which data was sent to which model and why.

8. Export and delete the selected memory with a testable receipt.

Scope to defer

Defer broad autonomous browsing, many messaging channels, multi-user sharing, fine-tuning, voice, shopping, payments, and generalized computer control. Each adds credentials, failure modes, or evaluation work. The first release should complete one workflow repeatedly, survive restart, and provide useful evidence of its behavior.

Hermes already offers memory and skill interfaces, including a learning timeline. A generic memory graph alone is therefore a weak novelty claim. [S11] Differentiate through temporal correctness, complete deletion across stores, controlled inference disclosure, and measured usefulness in the chosen workflow.

6 Architecture options and tradeoffs

Option A Managed NemoClaw and Hermes

Use a supported Linux host, a reviewed NemoClaw version, its compatible OpenShell release, Hermes, the memory API, and Token Factory. This offers a strong demonstration of credential isolation and declarative policy with less custom sandbox assembly.

The cost is operational complexity. NemoClaw is early-preview alpha, provides no production SLA, and has documented limitations for Hermes compatibility and host support. Linux Docker on Ubuntu 24.04 is the primary tested path; Windows WSL2 is tested with limitations. Native Hermes Windows support does not imply native NemoClaw Windows support. [S06]

Choose this if a clean integration trial passes and you can show actual policy denials, successful allowed tool calls, state restoration, and a documented reboot runbook. Treat continuous availability as something to demonstrate, not an automatic property of the framework.

Option B Hermes with a simpler deployment

Run Hermes on a supported host using its documented installation method. Expose a narrow memory API and task-specific tools. Use its own service and scheduler support, with operating-system and network controls appropriate to that deployment.

This reduces managed-stack dependencies and can be the fastest route to a complete product. It also transfers more isolation, credential handling and service ownership to you. Hermes supports native Windows, Linux/WSL2, macOS Apple Silicon and Docker as Tier 1 paths; PyPI and Homebrew installations are explicitly unsupported distribution methods. [S07]

Choose this if the managed stack blocks delivery. Describe the actual protections accurately. Ordinary Docker isolation and command approval do not establish parity with OpenShell's enforcement boundary.

Option C OpenShell directly with a custom agent image

Use OpenShell's current provider profiles and sandbox attachments, package Hermes in a custom image, and implement application-specific policy and service connections. This offers the most control over the runtime boundary and avoids assuming NemoClaw supports every topology.

It requires image maintenance, provider profiles, migration work, and more integration tests. It is appropriate if sandbox integration is central to the project's contribution and the team already understands OpenShell. It is a poor default for a solo builder with seven days remaining.

Option D Fully local models and memory

Local inference can keep prompts on user-owned hardware, but hardware, serving compatibility, model storage and power become constraints. A local-only application still needs qualifying Nebius runtime use for this hackathon. Use the local route for sensitive requests only if the system's meaningful Nebius integration is separately present and clearly demonstrated.

Recommendation: prototype B first, attempt A within a fixed time budget, and preserve B as the fallback. Avoid C and multi-node model hosting for this submission unless they are already working and evaluated.

The diagram is a proposed logical architecture. An “inference disclosure gate” is application logic you must implement and test; it is not a claim that these frameworks automatically redact arbitrary personal data.

Request sequence

Authenticate the user, resolve the workspace and permitted tools, retrieve a bounded set of authorized memories, and assemble only the context needed for the task. Apply the selected disclosure policy before inference. Ask the chosen model for a response or structured tool proposal. Validate tool arguments and authorization in code, execute if permitted, persist the result, and show the outcome with source references.

For writes, report success only after a durable acknowledgement. For external actions, use an approval record tied to the exact payload. For retries, use an operation identifier so a repeated request cannot create duplicate tasks, memory entries, or outgoing messages.

Recommended deployment split

Keep the agent gateway, scheduler, approval service and durable memory available on a persistent host. Use Token Factory for inference. Use finite Serverless Jobs only for optional batch evaluations or rebuildable indexing work. Place public demonstration data in a separate environment from personal memory.

This split costs more operational effort than a single process but prevents a stopped disposable workload from becoming a data-loss event. Start with one host and one memory backend if those satisfy the required tests. Add services only for a measured limitation.

8 Memory design and existing system integration

What Hermes already provides

Hermes's built-in memory consists of MEMORY.md and USER.md, with default limits of 2,200 and 1,375 characters. A session starts with a frozen snapshot; later writes persist but do not refresh that snapshot until a new session. Session search uses a separate SQLite history store. Memory and skill writes can be staged for approval. [S11]

Hermes external memory integrations are additive and can synchronize transcripts, recall context and mirror writes. This expands the data boundary. Secret scrubbing does not recognize every arbitrary password or opaque secret. [S12] Do not enable an external provider just because it appears in a catalog.

Choose the authority explicitly

If Iron Web is the project's contribution, make its memory service authoritative for user facts and decisions. Keep Hermes profile memory limited to non-sensitive operating preferences, or disable its built-in stores using the documented settings after validating the integration. Avoid simultaneous unsupervised writes to both systems.

For the first version, use explicit memory tools rather than a deeply coupled automatic provider plugin. A small API is easier to test, audit and replace. Add automatic prefetch or a native provider integration only when explicit tools demonstrably miss necessary recall.

Proposed durable record

Each fact should have an immutable identifier, subject and workspace, source identifier and source location, observed time, valid-from time, optional valid-until time, sensitivity, consent state, version, and deletion state. Keep model-generated confidence separate from source authority. A confident extraction from an untrusted page is still untrusted.

Distinguish a fact, a user preference, a hypothesis, a plan, an external document claim and an execution result. A user's correction should supersede a prior preference without deleting its audit relationship. A reminder is a task with a schedule and execution state, not merely a sentence stored in memory.

Retrieval and correction

Apply user, workspace, consent and deletion filters before retrieval, then combine lexical and semantic retrieval if needed. Return a small evidence bundle with record IDs, timestamps and source references. Resolve contradictory records using explicit authority and time rules. Ask when two equally authoritative current facts conflict.

Revalidate the bundle before composing the response if a deletion or correction may have occurred during inference. Cached responses should carry a memory revision so a correction invalidates stale answers. A hidden old copy in the current conversation can still influence output; the UI should support starting a fresh session after a sensitive correction or deletion.

If the current memory system uses several stores

If the implementation has a journal, vector database and graph database, keep the journal authoritative and treat the others as rebuildable projections. Record indexing checkpoints and idempotent event IDs. Test recovery when one index is behind or unavailable. A graph relationship must not silently override a newer journal fact.

If the existing code uses FalkorDB, Qdrant, SQLite or other named engines, their specific operational and license requirements still need a repository-level audit. This report did not inspect those deployed versions. Do not assume three databases are necessary for a small personal assistant. A simpler transactional store with full-text search may be sufficient for the first dataset.

Deletion must cover every copy

Define deletion separately for source documents, extracted facts, embeddings, graph edges, summaries, transcripts, generated artifacts and backups. Use tombstones so a delayed indexer cannot reintroduce removed material. Document backup expiry and ensure restores reapply tombstones before serving queries.

“Delete memory” should not promise immediate erasure from immutable backups unless the implementation can prove that property. Show the user which copies were removed, which are queued for expiry, and whether a new session is needed to clear live context.

9 Skills and controlled learning

Hermes skills are on-demand instructions stored under its skills directory. The agent can create or alter them, and hub installations go through security scanning. A scan is useful evidence, but it does not prove that a workflow is safe for your data or correct for your tools. [S13]

Create three small reviewed skills: review a paper, produce a source-linked project brief, and check a chosen commitment. Each skill should declare its inputs, allowed data sources, output format, required tools, stop conditions, and actions requiring user approval.

Example review procedure: extract the research question, method, evidence, limitations and relevance; identify unsupported claims; cite source locations; record a tentative conclusion; propose a durable memory only when it is useful beyond the current task. Keep the document's instructions separate from the user's instructions.

Enable skill write approval during the submission build. Let the assistant propose improvements after a repeated correction, then review a visible diff before activation. Version the accepted procedure and retain a rollback path. Successful execution should not automatically authorize a wider tool scope.

Treat executable scripts in skills as software dependencies. Pin their source revision, inspect changes, restrict write locations, and test malicious inputs. Avoid runtime installation from arbitrary skill repositories during the public demo.

These catalog link targets and prices are documented by Nebius. Its page lists Lightning as BF16 serving and Ultra as FP4 serving, with 1,024K context for both. This is provider-specific information, not proof of an account's current permissions or achievable context in every harness. [S14]

NVIDIA's corresponding model cards describe Lightning as 30B total parameters with 3B active and Ultra as 550B total with 55B active. Both use OpenMDW 1.1 rather than the application's prospective MIT or Apache license. Keep model licensing separate from application licensing. [S15] [S16]

Routing recommendation

Start with deterministic routing. Use Lightning for query classification, bounded extraction, drafting and routine retrieval. Use Ultra for reconciling evidence, difficult planning and final analysis where a small evaluation shows a material quality gain. Give each task a maximum number of tool turns and a token budget.

Do not let model-reported confidence alone trigger escalation. Prefer an invalid schema, insufficient evidence, contradictory sources, a failed verifier, or an explicit user request. A larger model is not permission to send more sensitive data. Apply the same disclosure rules before both routes.

Keep Ultra work in a short separate context where possible. Mid-session model switching can invalidate prompt caching and reread a large conversation. Configure auxiliary models deliberately; compression, title generation, reviews and routing can otherwise create extra inference and disclosure. [S17]

Compatibility checks

List models using the documented API and copy the exact case-sensitive identifiers. The verbose response can expose context, pricing and limits. [S18] Test text, actual structured tool calls, tool results, streaming, cancellation and structured JSON separately. API compatibility is not a guarantee that every feature combination works.

Both models need task-level evaluation under the actual provider precision and harness. A public benchmark is useful context, not your success rate. Nebius's October cookbook demonstrates cost measurement across Lightning, Super and Ultra and records a Deep Agents middleware workaround specific to Ultra; that workaround should not be copied into Hermes without reproducing a relevant problem. [S19]

Hosting models yourself

Ultra BF16's official card lists multi-GPU requirements including 8 H200 or 16 H100 GPUs. [S16] Active parameter count does not equal the memory needed to store all weights. Quantized deployments have different requirements and still need runtime and workload sizing. Hosted inference is the practical starting point here. Local Lightning may become useful later after checking the exact hardware recipe, available memory, context and concurrency. [S15]

11 Token Factory API integration

The documented base URL is https://api.tokenfactory.nebius.com/v1/ and examples use NEBIUS_API_KEY. [S20] This is a separate provider credential from an NVIDIA inference key. Store it in the host's approved secret mechanism; do not paste it into prompts, public repository files or client-side JavaScript.

For NemoClaw, choose the custom OpenAI-compatible endpoint path and use the Token Factory base URL and model ID. The adapter is tested with limitations; actual endpoint behavior requires validation. Onboarding may perform inference validation calls, so include them in the disclosure and cost model. Reasoning-only validation skips tool and streaming checks and is insufficient evidence for an agent. [S21]

Proposed integration sequence

1. Verify the account and billing, discover model IDs, and save a redacted capability snapshot.

2. Call each model directly with a harmless fixed prompt.

3. Define a minimal lookup tool and require an actual tool call with valid arguments.

4. Execute a deterministic local function, send its result back, and validate the answer.

5. Repeat through the selected sandbox; check that the effective route reaches Token Factory.

6. Test a source-linked memory retrieval and a draft artifact through the complete application.

7. Inject failures before enabling schedules or external actions.

The API returns function invocation proposals; your application executes them. [S22] Parse and validate the function name, arguments, subject permissions, expected object version, and permitted operation before execution. Never dispatch arbitrary model text as a shell command.

Use JSON Schema where supported and validate outputs again locally. A syntactically valid object can still contain a wrong date, invented source or unauthorized identifier. Some structured-output documentation examples reference older models or contain simplified snippets; export and test the exact request rather than copying examples blindly. [S23]

Failures and retry policy

Treat 401/403 as an authentication or authorization problem, 404 as a model or route mismatch, malformed requests as a caller bug, 429 as throttling, and temporary 5xx or connection errors as candidates for bounded retry. Respect server retry guidance and add jitter. Cap total elapsed time. Do not retry an external write unless its idempotency behavior is known.

Token Factory limits are dynamic and actual defaults are account-visible. Sudden bursts can throttle even if a marketing page quotes high throughput. [S24] Begin with low concurrency, queue background work, and show a clear “waiting for provider” state. Preserve pending tasks through an outage.

12 Security and privacy design

The privacy claim to make

“Your durable memory stays in the storage you choose. Hosted model calls receive selected context under the disclosure policy shown in the app.” This is a defensible proposed claim if implemented and tested. “Everything stays on your machine” would be false when hosted inference or cloud tools receive content.

Nebius advertises zero-retention inference and a mode where prompts and outputs are not stored or reused for training. [S25] The current public-endpoint documentation explicitly provides no fixed processing region. A region in an older blog or a region-looking base URL is not a residency guarantee. Dedicated endpoints are the documented path when location guarantees are required. [S26]

Validate the applicable account terms, endpoint mode, observability, data-lab imports, file uploads and any support logging before using sensitive real data. Zero-retention inference does not remove your application's transcripts, backups or connector logs. A certification advertised by an infrastructure provider does not certify this application.

What the sandbox adds

OpenShell separates a trusted supervisor from the agent workload, mediates network access, and binds provider credentials to permitted endpoints. The current architecture describes kernel controls and policy checking. [S27] These controls reduce the consequences of malicious instructions but do not make an allowed API call semantically safe.

An allowlisted inference endpoint can still receive private text. An allowed email API can still send the wrong message. A trusted MCP server can return malicious content or even reflect a credential it receives. Keep application authorization, disclosure checks and exact-payload approval outside the model's discretion.

OpenShell's current security guide distinguishes audit from enforce: L7 audit mode can log violations while forwarding traffic. TLS skip also removes inspection and credential rewriting for that endpoint. [S28] Inspect effective settings and test negative cases before claiming write blocking. Restrict broad interpreter grants, wildcard destinations, package registries and general web access.

13 Tools and MCP integration

Hermes supports MCP server discovery and tool selection. [S29] NemoClaw's managed MCP path is narrower: authenticated HTTPS Streamable HTTP endpoints, managed provider credentials, and explicit protocol policy. It does not launch an arbitrary host-side stdio bridge for you. Its current managed MCP documentation pins OpenShell 0.0.116. [S30]

Proposed memory tool contract

Expose operations such as memory_search, memory_get, memory_propose, memory_correct, memory_export and memory_delete through an authenticated service. Those names are proposed application tools, not existing built-in commands. Keep ordinary agent access to search and proposals; use a separate approval path for destructive changes and broad exports.

Every request should carry a validated identity context, workspace scope, request ID and a bounded result size. The server must derive authority from authenticated context rather than accepting a model-supplied owner_id as proof. Return typed errors for denied, missing, stale and temporarily unavailable records.

If the memory API is local to the host, container localhost is not the host's localhost. Use the documented bridge or a narrowly permitted private service endpoint. With managed MCP, verify trusted-private endpoint requirements, TLS, DNS behavior and tool filtering on the pinned version. A host-side successful request does not prove sandbox reachability.

Connector scope

Begin with selected local documents and one calendar or task source in read-only mode. Add draft creation in a separate workspace. External sending should show the exact recipient, content, attachments and consequence. Recheck scope at execution time, because a proposed action may wait while credentials or permissions change.

Prefer dedicated API tools over broad shell access for routine tasks. Restrict returned document size and remove unneeded fields. MCP transport encryption and tool descriptions do not replace authorization at the underlying service.

14 Always on operation and scheduling

Hermes runs scheduled tasks through its gateway daemon, ticking roughly every 60 seconds and creating isolated agent sessions. Its status command reports scheduler health and overdue work. Restart-safe workers depend on the deployment's service/session support; containers may degrade to workers that die with the gateway. [S31]

NemoClaw's headless guide explicitly requires manual recovery after host reboot and does not guarantee automatic restart of its gateway, sandbox and forwards. [S32] Do not claim unattended reboot recovery unless it has been separately engineered and tested within a supported deployment approach.

Define the availability promise

For the hackathon, target an assistant continuously reachable while its documented host is operating, with persistent jobs, visible last success, and recovery instructions. If reboot recovery remains manual, state that limitation in the product and submission. A laptop that sleeps cannot provide reliable unattended service.

Use one scheduler as the owner of a routine. Store timezone, next scheduled instant, last successful instant, task version and execution status. Choose a missed-run policy explicitly: run once after recovery, skip stale work, or ask the user. Do not replay every missed notification after a long outage.

Before a scheduled run starts, acquire a lease and create a durable run record. Check whether the same scheduled occurrence already completed. Apply a time budget and tool budget, store a draft, then notify only if there is meaningful new information or a failure requiring attention. These are proposed application controls; verify how they interact with Hermes's scheduler.

Required operational checks

Monitor scheduler heartbeat, memory health, disk space, queue age, inference errors, last successful backup and the availability of required connectors. Give the user pause and cancel controls. A cancel request should stop further tool actions and accurately identify any action that already happened.

Run a 24-hour soak before submission if time permits. Record real timestamps and restart events. A short accelerated schedule is useful for development but must not be presented as proof that a system ran for a day.

15 State durability and recovery

NemoClaw preserves the native home/workspace during routine lifecycle operations. Its rebuild path transfers that state through a bounded archive workflow and sanitizes local authority. Destroy removes managed state; the documented backup operation is not a general snapshot-management API. [S33]

Persistent sandbox state is not an independent backup. It does not protect against accidental deletion, host loss, compromised storage or a bug that writes bad data. Maintain separately encrypted, versioned backups and a restore procedure tested on an isolated dataset.

For SQLite, use a database-safe backup mechanism or quiesced snapshot rather than copying an actively changing database file alone. For a journal with derived indexes, preserve the journal and index checkpoints and demonstrate rebuilding the projections. Avoid live copying of secrets or machine-bound authority between sandboxes.

Define recovery targets as project goals: for example, no loss of acknowledged memory writes under process restart, and restoration of the synthetic demo within 15 minutes from a verified backup. These are proposed acceptance targets, not measured results or framework guarantees.

Test a restore with a corrected fact and a deleted fact. The restored application must serve the corrected value and continue honoring deletion. An apparently successful backup that has never been restored is insufficient evidence.

Deployment prerequisites

Serverless creation needs appropriate project IAM permissions, an image, a chosen platform/preset, networking and sufficient quota. The jobs guide supports CPU-only workloads, secret environment variables through SecretStash, bounded timeouts, mounted storage and injected configuration files. [S35]

Do not assume a platform can run NemoClaw's nested container and kernel isolation requirements just because it can run a container. Validate the entire topology. A normal Hermes application container and a managed NemoClaw host are different deployment artifacts.

Use a private registry or pinned public image digest, a dedicated service identity and minimal inbound access. Keep the memory database on suitable persistent storage. Use object storage for exports and backups rather than assuming object storage behaves like a transactional POSIX database volume.

Inference scenarios

ScenarioInput tokensOutput tokensLightning costUltra cost

At these token assumptions, 90 routine tasks on Lightning and 10 difficult tasks on Ultra cost about $0.4112. Escalating after an unsuccessful Lightning attempt adds the cost of that attempt. A multi-turn agent may reread growing history many times, so count all provider requests rather than only the user's initial prompt.

Costs that can dominate

Cloud Serverless uses Compute prices and quotas. Running resources and storage are billed; separately mounted buckets and filesystems remain separately billable. Stopped Devlabs retain disk charges. [S36] A self-hosted GPU running continuously can cost much more than a small number of API requests.

For planning, a hypothetical $0.10/hour host costs $72 for 30 days, while a hypothetical $2/hour GPU costs $1,440. These are examples, not Nebius quotes. Budget continued judging access as well as build-week usage. Obtain a region- and preset-specific quote before selecting paid compute.

Token Factory onboarding currently requires billing setup and a bank card; failed charging can suspend access. [S37] Promotional credit is not a guaranteed hard spending cap. Put limits in your application as well as any account controls available to you.

Proposed controls

Set separate budgets for interactive requests, schedules, background learning and evaluation. Start with a maximum of ten tool turns per routine task, a finite elapsed timeout and a visible cancellation path; tune these values from measurements. Limit Ultra escalation and preserve a queue when a daily background budget is exhausted.

Record model ID, input/output/reasoning usage where reported, request duration and retry count without logging full sensitive prompts. Reconcile estimates against the provider's billing view. Dedicated observability features should not be assumed available on public endpoints; the current observability guide limits its metrics to dedicated inference. [S38]

Model evaluation design

Create at least 30 fixed synthetic cases: ten retrieval/correction tasks, ten tool-use tasks and ten research synthesis tasks. Give each expected facts, required citations, forbidden actions and a deterministic completion check. Run both models on the same cases with the same evidence bundle and tool permissions. Repeat difficult or variable cases three times if budget allows.

Measure success, source correctness, stale-fact rate, unauthorized action count, schema failures, tool turns, p50/p95 latency and cost per successful task. Report sample size and failure examples. A model-written assessment can supplement the checks, but should not decide whether its own external action was authorized.

Proposed release targets: zero cross-user disclosures, zero unauthorized external actions, zero false confirmations of durable writes, and all required deterministic acceptance tests passing. Set a task-quality threshold before inspecting final results; 90 percent success on a small benchmark is a possible starting goal, not a universal reliability standard.

Evidence to publish

Publish commands, dependency versions, fixture descriptions, test timestamps and aggregate results. Include redacted provider/model identifiers and actual traces that prove qualifying runtime use. Keep synthetic failures visible. Separate “executed successfully,” “failed,” “not tested” and “unsupported” in the final test report.

22 Build prerequisites and starter runbook

What to prepare

Prepare a Devpost account, an approved Nebius account with working billing and inference credit, a public code repository, an operating budget, and a separate synthetic demonstration dataset. For the proposed managed stack, reserve a supported Linux host with at least 4 vCPU, 8 GB RAM and 20 GB free disk; the NemoClaw guide recommends 16 GB RAM and 40 GB free disk. It lists Node 22.19 or later and npm 10 or later. These are agent-stack requirements, not model-hosting capacity. [S09]

A GPU is unnecessary on the agent host when inference is remote. Add capacity for the actual memory databases, document processing and backups. Keep the model host, agent host and memory host conceptually separate even if two roles initially share one machine. For Windows development, use Hermes's supported native distribution or the documented WSL2 path for NemoClaw, with its platform caveats. [S07] [S06]

The application also needs an identity and session boundary, selected-source ingestion, a memory API, a draft workspace, an approval store, scheduler status, logging, backup storage and a user interface. Every connector added to this list needs its own account permission, disclosure decision and failure test. Create an inventory showing where each credential lives and which process can use it.

Start with provider discovery

The following Python example uses the standard library and the documented Token Factory discovery route. It is a proposed read-only diagnostic, not a test run performed for this report. It makes one authenticated network request when executed. Supply the key through the approved environment; do not paste it into the file. [S18]

import json
import os
import urllib.request

url = "https://api.tokenfactory.nebius.com/v1/models"
request = urllib.request.Request(
    url,
    headers={"Authorization": "Bearer " + os.environ["NEBIUS_API_KEY"]},
)
with urllib.request.urlopen(request, timeout=30) as response:
    models = json.load(response)

wanted = {
    "nvidia/Nemotron-3_5-Lightning",
    "nvidia/Nemotron-3-Ultra-550b-a55b",
}
available = {item["id"] for item in models["data"]}
print({model: model in available for model in sorted(wanted)})

A missing ID is a stop condition for that route, not a reason to guess a different spelling. Save the discovery timestamp and a redacted metadata snapshot. Then perform separate paid completion and tool-call checks using the provider's tested request format.

Use the installed version's Hermes model configuration UI or documented custom-provider schema. Avoid treating a generic YAML example as a universal configuration file. Hermes documents independent auxiliary routes and credential resolution; a base URL override can change where an auxiliary task sends data. [S41]

For a NemoClaw-managed setup, use its own onboarding and lifecycle commands to create the compatible environment. Enter the hosted custom endpoint and exact model explicitly. New default onboarding may select a different model from the one this project intends to demonstrate. [S08] [S39]

Daily operating runbook

Before a demo, verify account balance, provider health, memory read/write health, scheduler heartbeat, free disk and the last verified backup. Run one harmless actual tool loop and inspect the final result. Check the public demonstration environment from a fresh browser session.

If inference fails, preserve the pending request and diagnose account, model, DNS, timeout and provider status separately. If memory is degraded, refuse durable-save success and avoid confident personalized answers from incomplete evidence. If the host restarts, follow the selected stack's documented recovery sequence and check jobs before resuming notifications.

Before changing versions, create a verified backup, record the old manifest, upgrade an isolated copy and run the core acceptance matrix. During the submission week, avoid unrelated upgrades once the demonstration stack is stable.
